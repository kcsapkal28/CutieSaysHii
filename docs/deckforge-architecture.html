DeckForge · how it works

You give it a topic. It builds a slideshow as one HTML file.

DeckForge is a small app that runs on your own computer. AI helpers research the topic, write the story, then write the code for every slide. A real browser checks each slide before it is kept.

Your topic→ 6 AI steps, you approve each→ one deck.html file

The six steps of making a deck

Each step reads the files the earlier steps wrote and writes one of its own. Click a step to see what it does.

Changing your mind is safe.

If you edit or re-run a step, DeckForge deletes the files of the steps after it, because they were based on the old answer. Finished deck versions are never deleted.

Inside the Build step: write, look, fix

This is where the quality comes from. Every slide goes through this loop, and up to 6 slides are worked on at the same time.

1Builder writes

Sonnet

It gets the slide's script, the storyboard idea, your style, and 2–3 example slides that use a similar trick. It writes the slide as HTML, CSS and a little JavaScript.

2Rules check

Engine

A quick check that the slide follows the house rules: right size, own CSS only, no outside links. Broken slides go straight back to step 1.

3Screenshots

Chromium

The slide is opened in a real browser. Each animation step is photographed. Any error shown in the browser console is collected too.

4Critic reviews

Opus

It looks at up to 4 pictures and the errors, then says pass or fix, gives a score, and lists what is wrong.

If it passes

The slide is saved to slides/s03.html. Done.

If it needs a fix

The critic's list and the last picture go back to the Builder (step 1). That is one round. There are 2 rounds. If a serious problem is still left, the stronger Opus model gets one last try. The best attempt wins.

When all slides are done, the engine packs them into versions/1/deck.html together with the presenter code, 3D library, animation library and fonts. That is why the finished deck works with no internet.

Data flow: what happens when you press Run

Follow one click from your screen to the files on disk and back.

  1. Your browserasksStudio server

    You press Run. The page sends a request to /api/projects/<id>/stages/<stage>/run and keeps the connection open to receive a live feed of progress messages.

  2. Studio serverstartsEngine

    The server checks the project exists, then starts the work in the background and keeps a list of every message it produces. Because of that list, closing the tab or reloading the page does not stop the build. When you come back, you get the old messages replayed, then the new ones.

  3. EnginereadsProject folder

    The engine opens the earlier files (for example the script) and builds a clear question for the AI from them.

  4. EngineasksProxy → Claude

    The question goes to the local proxy, which forwards it to Claude. The answer must match a fixed shape (a schema). If it does not, it counts as an error instead of being saved.

  5. EnginewritesProject folder

    The valid answer is saved as the step's file, such as storyboard.json. Files of later steps are deleted, since they are now out of date.

  6. EnginereportsStudio server

    All along, the engine sends small progress messages ("slide 3, round 2, critic says fix"). The Studio translates them into its own message format, adds up the token use to estimate the cost, and forwards them to your browser.

  7. Your browsershowsYou

    You watch live progress. When the step finishes, you read the result, edit it if you want (edits are saved back to the same file), then click Approve to unlock the next step.

  8. Enginepacksversions/<n>/deck.html

    After Build, the finished deck is saved as a numbered version. The Studio serves that file to a viewer on the deck page. A chat edit on one slide runs the same loop for that slide and saves a new version, so you can always go back.

What a deck looks like on disk

Each deck is a folder. You can open any file in a text editor.

projects/why-the-moon-has-phases/
├─ brief.json          what you typed: topic, audience, minutes
├─ style.json          colours, fonts, how much motion and 3D
├─ research.md         facts the researcher collected
├─ outline.json        the list of slides and the story order
├─ script.json         what each slide says, and for how long
├─ storyboard.json     the picture/animation idea for each slide
├─ slides/             one finished HTML piece per slide (s01.html …)
├─ shots/              screenshots taken during the build loop
├─ versions/
│  ├─ 1/deck.html      the finished single-file presentation
│  └─ 2/deck.html      a later version after a chat edit
├─ build.json          scores and rounds for each slide
└─ studio.json         approvals, cost and logs shown in the Studio

Where the code lives

Folder or fileIn plain words
packages/forge/src/pipeline/The conductor. stages.ts runs the steps in order, build.ts is the write-look-fix loop, revise.ts handles chat edits and versions.
packages/forge/src/agents/One file per AI helper (stylist, researcher, script writer, storyboarder, builder, critic) and the shapes their answers must have.
packages/forge/prompts/The written instructions given to each helper. Slide quality depends heavily on these.
packages/forge/src/bundle.ts and shoot.tsPack slides into one HTML file; open it in Chrome and take screenshots.
packages/forge/src/shell/The small program inside every finished deck: arrow-key navigation, scaling to the screen, the 3D helper.
packages/forge/src/contract.tsThe shared rules and types. The "what is a slide?" definition.
apps/studio/app/The pages you see, and the api/ routes the pages call.
apps/studio/lib/server/Glue between the pages and the engine. real-backend.ts does the work; runs.ts keeps builds alive in the background.
start.shOne command to start the proxy and the Studio together.

Folders packages/harness, renderer, schemas, catalog belong to an older approach that is paused. You can skip them.

Good to know

  • Cost. A real 4-slide build used about $14 of model time. Making it cheaper is planned.
  • Stop button. It hides the live view but does not yet cancel the build on the server.
  • Server restart. A build in progress is lost if the Studio restarts. Finished decks stay on disk.
  • Research. The researcher uses what the model already knows. Live web search is not connected yet.
